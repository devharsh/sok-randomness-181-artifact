# Released artifacts: schema and provenance

This directory holds the machine-readable data underlying the SoK. Everything here is generated
and validated by `build_dataset.py` and `build_coverage.py` in the repository root. Running that script rewrites these
files and then cross-checks them against the LaTeX sources, so the paper and the released data
cannot silently diverge. It exits non-zero if any check fails.

Schema version 1.0.

## Files

`incidents.csv` and `incidents.json` hold the 28 systematized incidents. The CSV encodes
list-valued fields as semicolon-separated strings; the JSON keeps them as JSON arrays. Both carry
identical content.

`counterfactuals.csv` holds one row per incident (28 rows): the remedies judged to prevent it
(`preventing_remedy`), those that only detect or contain it (`partial_remedy`), whether a preventing
remedy was available when the vulnerable system shipped (`available_at_the_time`: `yes`, `partly`,
`emerging`, `no`, or `none_prevents` when no family in the catalog prevents it), and a one-line
reason (`why_absent`). The rows are generated by `build_coverage.py`, which also writes the coverage
matrix of the paper, so the matrix and this file cannot disagree. The grading rules are stated at
the top of `build_coverage.py` and in the paper.

`remedies.csv` holds the 14 remedy families with the pipeline stages each covers, whether it
prevents, detects, or contains a failure, its deployment friction, and its residual risk.

## Incident fields

`id` is a stable identifier used to join across files. `name`, `year`, and `domain` identify the
incident. `stages` lists the pipeline stages where the failure occurs, using `S1` entropy source,
`S2` accumulation and conditioning, `S3` generation algorithm, `S4` seeding and instantiation,
`S5` state lifecycle, `S6` consumption, and `S*` for the cross-cutting build and integration
surface. `root_cause` is a one-line technical description. `adversary` lists the applicable
adversary models: `T1` offline predictor, `T2` state recovery, `T3` consumption, `T4` subversion,
`T5` integration. `observability` is one of `silent` (output passes statistical tests),
`statistical` (detectable by testing or population analysis), or `external` (visible in public
data, for example a repeated nonce on a ledger). `radius` is one of `device`, `fleet`, or
`ecosystem`. `exploit_access` is the access an attacker needs to exploit the defect: `A1` remote
using public data only, `A2` local with physical proximity or on-device code execution, or `A3`
supply chain. `target_secret` records which secret the failure ultimately exposes, one of `long_term_key`,
`session_key`, `ephemeral_nonce`, or `generator_state`. This separates failures that compromise
long-lived key material from those that compromise a per-use value, a distinction the stage model
implies but does not state outright. `cve` carries the CVE identifier where one was assigned and
is empty otherwise. `dwell_years`
is the interval in years between the defect entering shipped code and its public discovery; it is
populated only where both dates are established by a primary source and left empty rather than
estimated, because public reporting rarely fixes the introduction date precisely.
`citation_keys` are BibTeX keys into `references.bib`, and `source` names the venue
or advisory in human-readable form.

Note that `adversary` and `exploit_access` capture different things and can differ for one
incident. The ColdCard case is coded `T5` because a build-integration process introduced the
defect, but `A1` because exploiting it required nothing beyond public blockchain data.

## Coding decisions and limitations

Each incident is assigned a primary stage set for clarity even though several span stages, and
the assignment reflects where the defect originates rather than where it is observed.
Observability and radius are coded from public reports, not from independent measurement.
The `radius` vocabulary permits `device`, but no incident in the corpus takes that value: every
documented failure is fleet-wide or ecosystem-wide. We retain the value rather than dropping it,
because its emptiness is itself a finding, discussed in the paper's incident section. A randomness
defect rarely stays local, since it lives in a design, a build configuration, or a shared library
that ships identically to every recipient. The
corpus covers publicly documented incidents only and is therefore biased toward failures that were
discovered and disclosed; silent failures still in the field are by construction absent. Research
demonstrations that did not affect a deployment, including the fault-injection and electromagnetic
attacks cited in the paper, are discussed in the text but deliberately excluded from this dataset,
which is restricted to deployed failures.

We excluded one widely circulated claimed attack because it could not be traced to any
peer-reviewed venue, CVE, or vendor advisory.

## Validation performed

`build_dataset.py` checks that the incident count matches the count claimed in the paper's table
caption, that every citation key resolves in `references.bib`, that every dataset incident appears
in the LaTeX incidents table, that the remedy count matches its caption, that every counterfactual
row refers to a real incident, and that the controlled vocabularies for observability, radius, and
access contain only permitted values. `build_coverage.py` checks that every incident has a coverage
row, that every prevent or partial judgment names a remedy whose stage set meets the incident's
stages, that R8 is graded by the observability rule only, and that availability is `none_prevents`
exactly when no remedy prevents the incident.
